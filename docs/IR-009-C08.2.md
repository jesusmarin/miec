# IR-009-C08.2 — contrato de actividad

## 1. Propiedad y tiempo

Cada proceso obtiene un executor_id UUID al construir ExecutionActivityService.
Cada inicio autorizado adquiere un fencing_token positivo de una secuencia global
de base de datos (no se reutiliza; los huecos por rollback son válidos).
La secuencia ordena adquisiciones también entre intentos de una misma acción.
El destinatario externo debe validar el token si se requiere fencing externo.
No se implementa transferencia, apropiación ni recuperación automática.

La base de datos es la referencia temporal para adquisición, renovación,
finalización y diagnóstico productivo. Las comprobaciones ocurren después de
adquirir el bloqueo de fila; se usa el reloj de pared de H2, no el inicio de
transacción. lease_expires_at == ahora significa vencido.
Vigencia inicial configurable: 30 segundos; heartbeat: 5 segundos. La frecuencia
debe ser menor que la mitad de la vigencia. Ambas transacciones son cortas.
Un heartbeat acredita actividad del supervisor, no progreso del trabajo.

## 2. Compatibilidad

V004 agrega campos opcionales sin actualizar registros existentes. Los cuatro
campos son todos nulos o todos informados. PENDING no tiene propiedad.
Los registros históricos IN_PROGRESS sin propiedad son INDETERMINADA y siguen
bloqueando reintentos. La aplicación nueva solo inicia con propiedad atómica.
Estados terminales retienen propietario, token y fechas para trazabilidad.
El despliegue debe detener las instancias antiguas antes de activar las nuevas:
no se permite operación mixta con código que omita las verificaciones.

## 3. Operaciones

El único inicio autorizado revalida plan y autorización IR-010 y adquiere
propiedad en el mismo commit. La vigencia de propiedad es independiente de
la autorización: no se promete cancelar un efecto iniciado si el permiso vence.
Heartbeat y finalizaciones requieren ejecución, propietario y token exactos,
estado IN_PROGRESS y lease vigente. El bloqueo de fila serializa renovación y
finalización. No se borra la propiedad ni se reabre un estado terminal.

El coordinador detiene el supervisor al terminar. Si una renovación falla,
solicita cancelación cooperativa por interrupción del hilo y conserva el fallo;
un ejecutor que ignora interrupciones puede continuar produciendo efectos.
La pérdida de propiedad jamás implica NO_EFFECT_CONFIRMED ni otro intento.
Si no se puede finalizar por vencimiento, permanece IN_PROGRESS para revisión;
la excepción del coordinador conserva el incidente. La persistencia de evidencia
tardía y la reconciliación corresponden a C08.3/C08.4.

## 4. Diagnóstico

ACTIVA: lease vigente. REVISION: lease vencido. INDETERMINADA: sin propiedad.
Son clasificaciones de lectura, no estados de ejecución. El criterio antiguo
por started_at se aplica exclusivamente a registros sin propiedad; los intentos
administrados requieren revisión por vencimiento aunque hayan empezado recién.

## 5. Validación por etapas

1. Contrato revisado y documentado.
2. Compatibilidad histórica y despliegue definidos.
3. V004: campos, restricciones, secuencia e índice; migraciones versionables.
4. Pruebas sobre base vacía y actualización V003 con registros históricos.
5. Adquisición, renovación, token y finalización bajo propiedad vigente.
6. Supervisor: renovación, cancelación y cierre sin tareas huérfanas.
7. Detector: activo, vencido y heredado sin escrituras.
8. Regresión completa en bases temporales; no tocar la base de desarrollo.

Todos los métodos de prueba nuevos deben tener Javadoc y DisplayName.

  Se quitó la regla de gitignore que excluía las migraciones.

- Paso 5: ExecutionActivityService y credenciales explícitas en las finalizaciones;
  34 pruebas asociadas aprobadas antes de integrar el supervisor.
- Paso 6: ExecutionHeartbeatSupervisor y coordinador; 25 pruebas aprobadas.
- Paso 7: clasificación por lease y tratamiento histórico; 35 pruebas aprobadas.
- Paso 8: regresión completa final, 616 pruebas, 0 fallos, 0 errores, 0 omitidas.
  Registro local: review-c082-regression.log (ignorado por Git).

La regresión usó bases H2 en memoria; no se arrancó contra data/miecdb.
V004 se aplicará a esa base únicamente cuando se inicie la aplicación actualizada.
La implementación del reloj y la migración son específicas de H2; otro motor
requiere una migración y una referencia temporal equivalentes.

Las APIs completeAttempt, failAttempt y markUnknown ahora exigen Ownership;
se eliminaron las variantes por executionId para evitar omitir las verificaciones.
El lease no sustituye IR-010. La reconciliación, la evidencia tardía persistente,
la transferencia y el fencing exigido por destinatarios externos siguen fuera
de C08.2. No se declara exactamente-una-vez para efectos externos.
